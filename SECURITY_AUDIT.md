# GOSH production security audit

Audit date: 2026-10-05. Scope: repository, locally available Git history, application routes, client Firestore access, and production build artifacts. No production data mutations or paid infrastructure changes are authorized or performed by this audit. Console configuration and deployed rules cannot be verified from this checkout.

## Phase 1 — boundaries (completed before fixes)

- Firebase email/password authentication remains the identity provider. Browser SDK login/signup/verification/password changes talk directly to Firebase; a separate Turnstile request is currently only a UI gate and cannot protect direct Firebase calls.
- `/api/auth/session` mints a 24-hour HttpOnly cookie from a recent, revoked-token-checked Firebase ID token; logout revokes refresh tokens and clears that cookie. Protected account/orders/checkout layouts require a server-verified cookie. Admin layout additionally reads `users/{uid}.role` on the server.
- Admin product/promotion/status/customer-summary/email/upload routes use trusted Firebase Admin verification and a database role, never a submitted role. Cookie mutations have Origin validation; Bearer mutations use non-ambient credentials. The legacy `lib/firebase/api-auth.ts` helper uses Bearer authentication only.
- Public API families: contact, newsletter, testimonials, Turnstile verification; active products/promotions. Protected APIs: checkout create/upload/receipt/delete, order emails, profile sync/session. No server actions or SQL database were found.
- Browser reads public active products, brands, testimonials and store settings; owners query orders by `user_id`; users read their own profile. Admin browser writes brands, brand linkage on products, message status, testimonial moderation, settings and notification-read state directly through Firestore Rules. These flows must remain supported with narrow rules.
- Admin SDK bypasses Firestore Rules: every server route needs its own authorization and validation. `users/{uid}.role` is the canonical trusted role; users cannot change it through existing profile rules.
- Ownership: `orders.user_id`, parent order ownership for `items`, and `payment_uploads.user_id`. Upload ownership was checked when viewing/deleting but NOT when attaching a receipt to an order.

## Confirmed pre-fix findings

### Critical
- Two service-worker source files loaded remote executable code from an unrelated third-party domain. No registration call was found in current application source; prior deployment/registration status is unknown. Treat any prior worker installation as an incident investigation item.

### High
- Checkout accepted arbitrary receipt URLs/file IDs, enabling cross-user receipt attachment and an SSRF path through the authenticated receipt proxy. Proxy followed redirects and relayed arbitrary content types.
- Cancellation checked stock restoration outside the transaction, permitting concurrent restoration more than once; checkout wrote stock before later transaction reads and repeated product lines did not aggregate quantities.
- An admin product form could overwrite stock changed by checkout while the form was open; saving now checks the observed stock in a transaction and returns 409 on a conflict.
- Rules allowed direct admin order/payment writes/deletion outside server state/stock validation, authenticated testimonial creation bypassing Turnstile/limits, and any authenticated audit-log creation.
- Product/promotion APIs accepted arbitrary objects/fields; insufficient ID, type, numeric, URL, date and request-size validation. Several API errors returned internal provider messages.

### Medium
- Production Redis outages/missing configuration silently degraded to per-instance rate limits; authentication session/profile and Turnstile endpoints lacked limits. Direct Firebase auth abuse requires provider configuration.
- Upload type checks trusted browser MIME and file names; direct ImageKit upload signatures did not constrain destination/type/size.
- Public Admin-SDK responses spread entire documents (including inactive embedded products/internal metadata). Firestore persistent browser cache could retain private orders on shared devices.
- CSP allowed production `unsafe-eval`; public promotions rules exposed inactive data; settings rules allowed arbitrary documents/fields; telemetry/errors could retain private context.

### Low
- Legacy X-XSS-Protection header, noisy diagnostic logging, permissive identifier handling, and no explicit backup/restore verification.

## Implemented defenses

- Compiler-enforced `server-only` guards now cover Firebase Admin, auth helpers, ImageKit, email, Turnstile and security utilities. Firebase Admin retains singleton initialization, project matching and malformed-key checks. Configuration failures do not fall back to unauthenticated access.
- Strict runtime schemas validate every JSON-consuming mutation API, nested product/decant/note/cart objects, enums, calendar dates, prices, quantities, bounded searches, URLs and document IDs. Requests reject unexpected/prototype/privileged keys, wrong types and bodies over 64 KiB, including streamed bodies without Content-Length. Profile/session endpoints ignore submitted identity fields and derive identity from Firebase. Existing form validators remain; no Zod dependency previously existed.
- Receipt attachment verifies ownership inside the order transaction, binds a file to one order, and blocks deletion/reuse after attachment. Deletion claims prevent an attachment/delete race. New orders retain their receipt file ID and store an authenticated proxy path. Legacy receipts are fetched only from this ImageKit account's payment folders, with redirects disabled, a timeout, 10 MiB response limit, image-only types, sandbox CSP, nosniff and private/no-store caching. Foreign receipts return 404.
- Checkout aggregates repeated product IDs, reads all transaction data before writing, checks finite nonnegative prices and total stock, and computes money/identity/state exclusively from trusted records. Per-user idempotency keys are transactionally bound to request fingerprints. UI submissions send a fresh key; replaying the same request/key reserves stock once. A deliberate new submission with a new key remains a new order.
- Cancellation restores all debited quantities once in the same transaction as order state; cancelled orders cannot be reopened after restoration. Payment/order updates and audit records commit atomically; payment documents stay synchronized. Order-status emails require the current trusted transition. Durable per-event email leases prevent ordinary duplicate/concurrent sends; crashes between provider delivery and recording completion can still cause retry duplicates.
- Product/promotion fields are allowlisted, including the existing product story/notes fields. Product updates require an observed stock value and compare it transactionally before changing inventory. Destructive brand/testimonial operations now use authenticated server endpoints and record the actor. A brand with linked products is deactivated based on a server query, never cascaded into product deletion. Image cleanup follows database persistence and is confined to permitted ImageKit folders. Existing confirmation UI remains.
- All admin APIs still use Firebase token/session verification plus the current `users/{uid}.role`. Protected access rechecks user existence/disabled state and current verification. Trusted legacy unverified administrators remain supported to preserve existing access; verify these accounts before launch. No request role, UID or localStorage value grants privileges.
- Cookie mutations require exact approved Origin and matching Host; forged Host/external Origin pairs fail. Production defaults are the primary www origin and bare domain; development allows loopback only. Preview/additional origins require explicit configuration. No wildcard/private API CORS was introduced. Logout revocation and HttpOnly/Secure/SameSite=Lax/Path=/24-hour cookies remain.
- Redis Lua limits are atomic/shared; production fails closed when Redis is absent/unavailable, with development-only memory fallback. Limits now cover session/profile synchronization, Turnstile verification, expensive catalog APIs and admin operations, in addition to reset/contact/newsletter/testimonials/checkout/uploads/email. Redis identifiers are hashed. This does not prevent attackers calling Firebase Auth directly.
- Public API responses select display fields and omit administrative/image-deletion metadata; inactive embedded products are excluded. Public customer/admin text uses React escaping, emails escape HTML, historical social/CTA URLs are screened, redirects reject external/control/encoded-separator targets. No SQL code/dependency was found: classical SQL injection is not applicable to Firestore. Collection/query-field names are fixed by code, not request input.
- Firestore uses memory cache instead of persistent IndexedDB for future private reads. Production browser diagnostics are gated/minimal; provider errors never become public error messages. Sentry strips request/user/extra/context/breadcrumb information and exception messages, with error replays disabled. This does not erase historical logs, caches or telemetry.
- Unrelated remote service-worker loaders were replaced with an unregistering retirement worker; `/sw.js` is served without caching and clears origin Cache Storage on activation. Historical registration/compromise remains unverified.
- CSP retains required Firebase, ImageKit, Turnstile, analytics and optional reCAPTCHA connections; production removes `unsafe-eval`, preview scripts are preview-only, workers are self/blob, objects are denied and frame ancestors denied. Existing HSTS, nosniff, Referrer-Policy, Permissions-Policy and frame-denial headers remain; private pages/APIs are no-store. X-Powered-By is disabled, legacy X-XSS-Protection is set to 0. **Exception:** `unsafe-inline` scripts remain for existing static Next hydration/theme/analytics; styles remain inline for current styling/motion. A nonce-based rendering migration is deferred, not claimed implemented.
- Next.js and lint config updated to 16.3.8; compatible dependency fixes and same-major gRPC/brace-expansion overrides applied. Firebase authentication was preserved. Production dependency audit: zero known advisories. Development: five high affected-package entries from one `braces`/glob/lint chain; no safe advisory-suggested fix without downgrading the lint stack. Do not run untrusted glob patterns through those tools. No critical/medium/low production dependency advisories remain in the recorded scan.

## Firestore Rules decisions (deploy separately)

| Collection / subcollection | Client reads | Client writes |
| --- | --- | --- |
| `users` | Own profile, including verification flow; admin | Bounded name/phone + server timestamp only. No create/role/identity/delete |
| `products` | Active public; all admin | Admin brand linkage + timestamp only; content/stock/price/create/delete server-only |
| `orders`, `orders/{id}/items` | Verified owner by `user_id`/parent owner; admin | Admin order `is_read` acknowledgement only; all item/state/money/create/delete server-only |
| `payments` | Admin | Server-only |
| `payment_uploads`, `order_requests`, `email_deliveries` | None | Server-only |
| `messages` | Admin | Enum message status only; submissions server-only; no direct deletion |
| `testimonials` | Active public; all admin | Validated admin moderation only; submission/deletion server-only |
| `brands` | Active public; all admin | Bounded admin create/update; deletion server-only |
| `promotions`, `product_promotions` | Active public; all admin | Server-only |
| `website_settings` | Intentionally public storefront/business content | Admin allowlisted bounded fields/HTTPS URLs; no delete |
| `site_settings` | Public singleton `1` only; merchant payment instructions are intentional | Admin allowlisted bounded fields/booleans/prices/HTTPS URLs; no delete |
| `newsletter_subscribers` | Admin | Server-only |
| `admin_notifications` | Admin | Boolean read acknowledgement only |
| `audit_logs` | Admin | Server-only append; no client forgery/update/delete |
| Anything else, including unlisted subcollections | None | None |

Rules cannot redact fields: public collections must contain only public data. Stock remains directly readable in active product documents because current storefront Firebase queries need it; public API serialization omits it. Do not place internal costs, credentials, customer details or draft-sensitive content in those documents. Admin role assignment/removal must remain a controlled Console/Admin operation. Rules do not automatically revoke already-issued Firebase ID tokens on cookie logout; Admin endpoints check revocation, while direct SDK access may persist until token expiry/provider invalidation. Demotion of the canonical role takes effect through Rules.

## Required Vercel / environment actions

- Confirm server-only Firebase Admin/ImageKit/Turnstile/Redis/email/Sentry credentials in environment settings; never prefix them with `NEXT_PUBLIC_`. Public Firebase client config, ImageKit public key, Turnstile/reCAPTCHA site keys and Sentry DSN are intentionally public. Use least-privilege service-account IAM and keep secrets out of logs/preview exports. Rotate any credential separately if provider review establishes exposure.
- Configure working Upstash Redis credentials in every production deployment and alert on outages/denials. There is **no production in-memory availability fallback**; missing Redis intentionally stops protected abuse-sensitive operations. Vercel must overwrite forwarded IP headers; another hosting/proxy stack must implement the same trust boundary. [Vercel headers](https://vercel.com/docs/headers/request-headers) documents this platform behavior.
- Register production Turnstile hostnames; set `TURNSTILE_ALLOWED_HOSTNAMES` for deliberate additional hostnames and `SECURITY_ALLOWED_ORIGINS` for exact approved origins. Do not add broad wildcards. Configure email provider delivery and test reset/verification/order emails without logging links or customer payloads. The SDK reset/resend calls remain provider-controlled and can bypass application quotas.
- Smoke-test actual domain headers, password auth, private receipts, all supported images, analytics, Turnstile and optional App Check after deployment. CSP's inline-script exception remains a medium defense-in-depth limitation. Vercel request-body limits may be lower than the application's 10 MiB image limit; verify the plan/platform limit before advertising supported upload sizes.
- Restrict Sentry dashboards/retention and review historical telemetry. Consider disabling performance traces if sensitive URLs enter transaction names; `beforeSend` strips error-event private context, not every possible performance integration. Monitoring integrations/third-party scripts remain trusted supply-chain dependencies.

## Data loss / backup / recovery

Critical records: `users`, `orders` plus `items`, `payments`, `payment_uploads`, inventory/products, promotions, brands, store settings, contact/newsletter records and audit logs. `order_requests` contains private idempotency results; `email_deliveries` contains delivery-control metadata. Back up ImageKit private files separately and manage Firebase Auth user export/recovery separately from Firestore.

No backup configuration was verified or enabled. After billing approval, select daily scheduled backups with retention appropriate to the business, consider PITR, restrict backup/restore IAM, and record a recovery owner/RPO/RTO. Before any bulk migration, export and verify a restore into a separate database/project; reconcile inventory/order/payment consistency and file IDs, then switch through a reviewed recovery procedure. Never overwrite live data blindly. [Firestore backup documentation](https://firebase.google.com/docs/firestore/backups), [PITR setup](https://firebase.google.com/docs/firestore/use-pitr) and [billing](https://firebase.google.com/docs/firestore/pricing) describe external configuration and charges.

No order/customer cascade-delete endpoint exists. Server product deletion preserves order item snapshots; brand deletion does not delete products. Existing legacy-brand conversion/unlinking uses multiple client updates and can partially succeed; export first and rerun/reconcile failures. Notification mark-all uses a batch; large lists can exceed Firestore batch limits without deleting records. Settings/products use merge writes; strict writable-field selection reduces accidental overwrite. Receipt cleanup is allowed only before attachment. Monitor orphaned uploads/deletion leases after process crashes; cleanup must verify ownership/state before removing anything. Audit logging of product/promotion CRUD is best-effort and reports a generic server failure if logging is unavailable; critical order/payment/brand/testimonial transactions include audit writes atomically.

## Verification and practical limits

- 111 isolated authentication/security tests pass, including anonymous/admin denial, cross-user receipt/email access, role/status spoofing, malformed/oversized bodies, path IDs, unsafe URLs/redirects, escaped XSS text, destructive authorization, repeated stock lines, concurrent cancellation, stale admin inventory conflicts, preserved product story fields, idempotency and duplicate email delivery. No real production users/data were mutated.
- Firebase repeated-initialization test passes. TypeScript passes. Lint: zero errors, two existing navigation warnings. Final Next.js 16.3.8 production build passes (47 static generation entries). Local production HTTP smoke passes: 13 protected mutation endpoints deny anonymous callers, four private page layouts redirect to login with no-store caching, security headers apply, and the retirement worker has no remote loader. Next streams these page redirects after a public loading shell (HTTP 200 with a server redirect instruction); this is not an authenticated page response. Existing headers check: 8/8 pass, no warnings. Live authenticated provider/browser flows still require staging verification.
- Rules suite: 36 cases authored, but execution was blocked by missing local Firestore emulator/Java setup. The failed prerequisite caused all test hooks to fail; **no rule enforcement result is claimed**. This remains a launch gate.
- Existing static accessibility checks: loading announcements 12/13; landmarks 14/17. Failures are in unchanged UI sources and stale path/utility assumptions. Interactive/manual accessibility and real Firebase/Admin/ImageKit/Turnstile browser flows were not claimed verified.
- Secret scan: 278 tracked files, 294 tracked/new worktree files and 1,734 reachable text/path Git objects examined; ignored local environment files are untracked. No service-account/key files were found outside ignored dependencies/build/cache/Git internals. No actual application credential material found. A historical repeated-character GitHub-token placeholder and Firebase Admin error-name constants were reviewed as false positives. Scans cannot prove absence in unreachable Git objects, provider dashboards, old deployments, logs or remote forks. Final 1,113 client/server bundle artifacts (including artifacts generated by local HTTP smoke) were checked for private-key/service-account material, server-env markers in client assets and literal current credential values; zero findings, no values printed.
- Dependency scans are point-in-time registry results, not a guarantee of safety. No destructive production tests, paid provisioning or silent Console enforcement was performed. This is defense in depth, not perfect security.
